# 1. Архитектура

## Общая схема

```
[PWA / браузер]
   getUserMedia → canvas → JPEG blob
        │ HTTPS, JWT
        ▼
[API Gateway: Express]
   auth · tasks · assignments · submissions · profile · leaderboard · admin
        │
        ├── Prisma → PostgreSQL         (пользователи, задания, сабмиты, статистика)
        ├── Storage driver → S3/MinIO   (оригиналы фото + превью)
        ├── Redis                       (сессии камеры, rate-limit, кэш лидерборда, очередь)
        └── AI Service
              ├── generateTasks()  → claude-haiku-4-5-20251001
              └── verifyPhoto()    → claude-sonnet-5 (vision)
```

## Почему так

**Монолит на старте, а не микросервисы.** До ~50k DAU один Express-процесс за балансировщиком
дешевле и быстрее в разработке. Точки будущего разреза уже вынесены в отдельные модули:
`services/ai`, `services/storage`, `services/antifraud` — их можно вынести в сервисы без
переписывания роутов.

**Проверка синхронная, но с таймаутом.** Игрок ждёт вердикт 3–8 секунд — это часть геймплея,
асинхронная очередь ломает ощущение. При превышении `AI_TIMEOUT_MS` сабмит уходит в
`PENDING` и добирается воркером, игрок получает уведомление.

**Дешёвые проверки — до ИИ.** Пайплайн отсекает дубли, размытие, скриншоты и просрочку
локально (sharp + pHash), и только выжившие ~70% запросов уходят в vision-модель. Это
основная статья экономии: вызов vision дороже локальной проверки на три порядка.

## Слои бэкенда

| Слой | Файлы | Ответственность |
|---|---|---|
| Routes | `src/routes/*` | HTTP, валидация (zod), коды ответов |
| Services | `src/services/*` | Бизнес-логика: ИИ, антифрод, скоринг, достижения, хранилище |
| Lib | `src/lib/*` | Инфраструктура: prisma-клиент, image-утилиты, jwt, errors |
| Middleware | `src/middleware/*` | auth, роли, rate-limit, обработка ошибок, загрузка файла |

Правило: роут не ходит в БД мимо сервиса, если операция сложнее одного `findMany`.

## Жизненный цикл задания

```
Пул заданий (генерирует ИИ, наполняется по cron)
   → игрок принимает задание  → Assignment{ACTIVE, nonce, expiresAt}
   → открывает камеру         → CaptureSession{token, ttl 5 мин}
   → снимает и отправляет     → Submission{PENDING}
   → пайплайн проверок        → APPROVED (очки, XP, ачивки) | REJECTED (причина, попытка)
   → выдаётся следующее задание
```

`nonce` привязывает фото к конкретной выдаче задания, `capture token` — к конкретной
сессии камеры. Без обоих сабмит не принимается: это делает бессмысленной отправку
файла из галереи через curl.

## Масштабирование

1. **0–5k DAU** — 1 инстанс API, managed Postgres, S3. Хватает VPS 2 vCPU.
2. **5–50k DAU** — 3–5 инстансов API за ALB (stateless, JWT), Redis для rate-limit и
   лидерборда (ZSET), CDN перед превью, отдельный воркер для догоняющей проверки и cron.
3. **50k+ DAU** — вынести `ai-verifier` в отдельный сервис с очередью (BullMQ/SQS) и
   собственным пулом лимитов Claude API; читающие реплики Postgres для лидерборда и
   истории; шардирование фото по бакетам `photos/{yyyy}/{mm}/{userId%256}/`.

Узкое место всегда одно — rate limit vision-модели. Лечится батчингом превью,
кэшем по pHash (одинаковое фото не проверяем дважды) и деградацией: при исчерпании
лимита включается «отложенная проверка» вместо отказа.

## Безопасность

- JWT access (15 мин) + refresh (30 дней, ротация, хранится хэш).
- bcrypt, cost 12. Пароль минимум 8 символов, проверка по списку топ-10k утечек.
- Rate limit: 5 логинов/мин на IP, 30 сабмитов/час на пользователя, 200 API-запросов/мин.
- helmet, CORS whitelist, размер загрузки ≤ 8 МБ, разрешены только `image/jpeg|png|webp`.
- Фото не отдаются публичным URL — только через подписанные ссылки на 10 минут.
- Роли: `PLAYER` / `MODERATOR` / `ADMIN`, проверка в `middleware/roles.js`.
- Все действия админа пишутся в `AuditLog`.
